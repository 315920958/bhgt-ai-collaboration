## 0. 三项目总览与依赖方向

| 项目 | 角色 | 依赖 |
|---|---|---|
| **bhgt-server** | 数据 + 逻辑中枢（Mongoose 模型、战斗判定、评分、按钮随机、重生、临时状态、灵石收支、境界突破、各配置 CRUD 接口、玩家存档接口） | 无（最先动，定义接口契约） |
| **bhgt-admin** | 后台配置界面（左侧菜单 + 各配置页壳），把 server 的接口可视化 | 依赖 server 的配置 CRUD 接口就绪 |
| **bhgt-h5-client**（本地 `bhgt-cocos-client`） | Cocos 玩家端（登录/剧情/角色/商店/战斗结算/本世结算/天赋/CG） | 依赖 server 的玩家存档与节点/战斗接口就绪 |

**跨项目顺序原则**：server 先定义数据模型与接口契约 → admin 与 Cocos 玩家端并行对接。最短可玩 Demo 路径 = `server 基础数据+节点战斗+重生` + `Cocos 主链路`；admin 初期可手动插库，但建议同步做基础数据配置页以便可视化。

## 1. 已澄清、可直接落地的硬结论

1. **阶段即卷**：玩家看到的「第 N 卷」= 大阶段顺序，不单独配置卷名。
2. **境界突破在小游戏里**：采用小游戏形式（剧情设定第 8 节已确认）。
3. **寿元 = 健康度（HP）**：战斗失败扣寿元，归零重生；与年龄无关。
4. **灵石收支无公式**：= 所有已配置「灵石变化」字段的累加。
5. **临时状态 = 数组存储**：每项 `{属性, 变化值, 剩余节点数}`，叠加、单独到期、重生清空。
6. **炼丹是小游戏之一**：其「灵材」是小游戏内部输入，不进物品配置。
7. **本世评分仅由「战斗」+「小游戏」产生**：普通剧情事件节点（选项按钮）不加不减本世评分。

- 配置项（`@nestjs/config` 多 env）齐全：DB_NAME、AUTH_AES_KEY、token 过期。

### S1 基础数据模型 + 配置 CRUD（无依赖，做扎实）🔧 正在开发中

- 对应模块的 CRUD 接口 + DTO（供 admin 调用）：`/admin/attributes`、`/admin/items`、`/admin/talents`。
- 默认值：第三特殊属性、悟性先留「待定」字段。

### S2 节点 / 大阶段 数据模型 + CRUD（优先级前置 · 🟡 待开发）
> 前置说明：以下数据模型与 CRUD 的 schema 已详细设计（§6.2 大阶段 / §6.3 节点+按钮），不依赖战斗算法，已获批准前置；**验收后即开发**。接口契约见 §8.1（与 admin 配置页成对）。核心算法逻辑见 S2b。
- `config.stages`（大阶段/卷）模型 + 接口（`/admin/stages`）
- `config.nodes`（含 buttons 子文档）模型 + 接口（`/nodes`、`/admin/nodes`）；按钮随节点子文档管理
- Mongoose schema 严格照 `database-schema.md` §6.2 / §6.3
- **📝 数据已预置（2026-08-05）**：`config.stages` 已直接通过 mongosh 写入开发库 `bhgt_test`（5 条：婴幼儿/少年/青云宗/黑风谷/落云海，字段照 §6.2、按 `code` 幂等 upsert）。此为**纯数据预置**；server 的 `stages` Mongoose model / controller 仍未实现，待 server 对话补上即自动可读。CRUD 接口仍标 🟡 待开发。

### S2b 节点 / 按钮 核心算法（依赖 S1，仍按 S2 节奏）
- **核心算法（纯 TS 模块，与 UI 解耦）**：
  - 按钮筛选：过滤不满足开启条件 → 必现占坑 → **权重轮盘赌补足（概率 = 该按钮权重 / 全部候选权重之和，Q7 已确认）**。
  - 战斗判定：属性全过门槛→成功；不足→**气运补差（分档/取整由配置决定，Q6 已定方向：保留气运补差、规则看配置）**→投掷次数重试。
  - 评分：Σ 超额属性点 → 档位 → 档位分值 × 全局乘数（**普通节点不加评分、无扣分、只有正向分，Q4 已确认**）。
  - 临时状态：数组 `{属性,变化值,剩余节点数}`，叠加、单独到期、重生清空。
  - 灵石收支：各配置灵石变化字段累加（无公式）。
  - **调试专用（仅非生产）**：dev 模式下提供「重新生成该节点数据」能力（节点数据由 `/game/node` 生成、按钮随机筛选结果存服务端；dev 下允许强制重新生成，便于看不同随机结果）。生产环境（NODE_ENV=production）**不暴露**此能力。

### S3 境界数据模型 + CRUD（优先级前置 · 🟡 待开发）
> 前置说明：境界 schema 已详细设计（§6.1），不依赖突破逻辑，已获批准前置；**验收后即开发**。Mongoose schema 严格照 `database-schema.md` §6.1。
- `config.realms` 模型 + 接口（`/admin/realms`）：等级→境界名→突破寿元/可分配属性点/单项上限。

### S3b 突破与重生逻辑（依赖 S1/S2，仍按 S3 节奏）
- 突破发放属性点：每种属性点独立字段、加权值（Q2 已确认需做「分配属性点」界面，数据模型先建）；突破以「小游戏形式」触发，前期 server 返回模拟档位。
- 重生逻辑：本世结算 → 选 1 遗物永久保留 → 清临时状态 → 回起始节点，保留 CG/永久遗物/天赋点。

### S4 玩家存档与游戏接口（依赖 S2/S3）
- game.users 扩展字段：昵称、性别、年龄（从 0 起，每过一回合 +1，固定，Q9 已确认）、境界、寿元、灵石、属性、临时状态数组、已生效天赋、CG 解锁列表。
- 接口：`/game/start`（新游戏，读开局配置）、`/game/node`（取节点+筛选后按钮，结果存服务端）、`/game/battle`（战斗判定+结算）、`/game/settle`（本世结算+重生）、`/game/cg`、`/game/role`。

### S5 小游戏接口（最后，依赖全部）
- 前期：节点/突破调用的小游戏返回模拟档位（第一档/第二档/第三档/失败）。
- 正式：转盘（分区概率+加码）、答题（题目/计分）、炼丹（配方+炸炉）配置与判定，放最后做。
